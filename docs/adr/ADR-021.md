# ADR-021: Data protection architecture, part 1: tenant isolation by forced row-level security

Status: Accepted in part
Date: 2026-11-14

## Context

ARCHITECTURE decision D8 and section 15.3 isolate one account's records from another's by two
means: PostgreSQL row-level security and the per-account data key. The data key was built first
(ROADMAP G2.4, G2.4b; ARCHITECTURE section 15.2, "As built"). This record covers the first means,
built in ROADMAP G2.3 as migration V14, on a schema that was already live with the owner's data.

Three facts shaped it:

1. The application connected as the login role that owns the schema. On the stock container image
   that role is a superuser, and a superuser bypasses row-level security even when it is forced.
2. The unit of work opened every transaction without knowing the account. The chat learns the
   account inside the transaction, from the sender's Telegram identity; the loops, the outbox
   dispatcher, the sweepers and the purge replay act across accounts by design.
3. The baseline is frozen (ADR-002 addendum). The change had to be one new migration that upgrades
   the live database in place and leaves the previous release able to run against it.

## Decision

**Roles and the claim.** Every transaction of the unit of work, and every short statement of the
stores of the edges, takes a role with `set_config('role', ..., true)`, so the role ends with the
transaction and a pooled connection never carries it further:

| Role | Used by | Sees |
|---|---|---|
| `dosegram_app` | `UnitOfWork.transactionAs(account)`; `Tx.actAs(account)` | The rows whose account is the claim `app.account_id`; with no claim, no row |
| `dosegram_worker` | `UnitOfWork.transaction` | Every account. It is a member of `dosegram_app` for its grants, and nothing more |
| `dosegram_erasure` | the erasure job, as before | Every account; deletes where V12 granted it |
| the schema owner | migrations and the start-up stages | Every account, by an explicit policy |

None of them is a superuser, has `BYPASSRLS`, may log in or owns a table (SEC-09, asserted by
`RlsSuite`).

**Policies.** Every account-owned table has `ENABLE` and `FORCE ROW LEVEL SECURITY` and four
policies: `tenant_isolation` for `dosegram_app` on `<account column> = dosegram_current_account()`,
and `cross_account_worker`, `erasure_job` and `schema_owner` that admit every row for their role.
A table whose account column is nullable (a row of the onboarding, written before the account
exists) accepts such a row from the application role but never shows it through the claim.
`schedule_revisions` names its account through its schedule. `dosegram_protect_account_table`
creates the four policies; the migration that adds an account-owned table calls it, and
`RlsSuite` fails for a table that is neither protected nor listed with its reason.

**Who binds.** Every Mini App route runs its transactions with `transactionAs` for the session's
account; only the session exchange (which authenticates by the Telegram identity) and the download
ticket (which authenticates by the ticket) run across accounts. A chat update resolves its sender
first and then binds the transaction to the sender's account; the onboarding, before the account
exists, stays across accounts. The loops, the dispatcher, the sweepers, the purge replay and the
stores of the edges are the documented cross-account work of section 15.3.

**Upgrade in place.** V14 revokes nothing. A superuser login role needs nothing. A login role that
is not a superuser is granted the three roles by V14 when it created them, and otherwise start-up
refuses to serve and names the `GRANT` the owner runs (OPERATIONS section 10). The previous
release keeps working against V14, because it runs as the schema owner.

## Consequences

- A repository method that forgets its account filter, or takes only an object id
  (`medications.get`, `occurrences.get`), cannot reach another account's row from a route or a
  bound chat update: `CrossTenantSuite` proves it table by table and repository by repository.
- The cross-account work is not limited by the policies. Section 15.3 planned `SECURITY DEFINER`
  claim functions that return identifiers only, with a per-row binding inside the worker; that is
  a later step, recorded in ROADMAP Appendix B. Until then the narrowness of `dosegram_worker` is
  its grants (no ownership, no DDL, no `BYPASSRLS`) and the code paths that use it.
- The stores of the edges (Mini App sessions, idempotency keys, the inbox, images and file ids)
  run as the worker: the session lookup authenticates by token before any account is known.
- Each transaction costs one more round trip (`set_config`). The claim query keeps
  `ix_occ_next_action`; the measurement is in ROADMAP Appendix B, G2.3.
- Row-level security guards against a programming error, not against arbitrary SQL from the
  application's own connection: such SQL can set the claim. The data key is the second means.

## Alternatives considered

- **`SECURITY DEFINER` claim functions for every loop now.** Rejected for this step: it rewrites
  each loop's queries and their tests at once, on a live schema; the role split gives the same
  protection to the routes and the chat, which are the paths that take identifiers from a user.
- **Fail closed by default** (`UnitOfWork.transaction` as `dosegram_app` with no claim). Rejected
  for this step: about 60 cross-account call sites in the loops would each need a decision in the
  same change. The Mini App module is bound by construction and checked by `CrossAccountSuite`.
- **Not forcing row-level security, letting the owner bypass it.** Rejected: the explicit
  `schema_owner` policy shows the exception in `pg_policies`, and `FORCE` covers any other owner.
- **A schema or a database per tenant.** Rejected in ARCHITECTURE section 21 (ADR-021 summary).

Supervisor decision, 2026-11-14 (the owner delegated every decision).
