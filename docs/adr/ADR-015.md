# ADR-015: Chat boundary for a Telegram-native product

Status: Accepted
Date: 2026-11-13

## Context

`contracts` and `core.chat` were symbol-neutral but still modelled the retired vendors: a deferred interaction with a reply hook, declared visibility, typed command options, reactions as controls, a native select menu and a modal form (research brief 01, section 4, findings 3 to 10 and 13 to 14). The same contract could not express a photo with a caption, a button that opens the Mini App or a URL, a deep-link payload, or media that a user sends. ARCHITECTURE section 6 lists the revision as rows C3 to C12.

ROADMAP schedules the removals as slice G0.6 and dissolves the additions (G0.7) into the slices of their first consumers. The owner has since started four tracks in parallel (transport, rendering, media and the Mini App path). Each needs the same contract at the same time, so the additions that those tracks consume were made together, right after the removals, and the result is frozen here. The additions that no track consumes yet stay with their consumer slices.

## Decision

The chat boundary is the surface below. A change to it is a serialised change with an addendum to this record.

### Removed

| Element | Removed | Row |
|---|---|---|
| `InteractionHandle` | `deferUpdate`, `deferReply`, `respond`, `openForm`, `replyAvailable`, `modalAvailable` | C4 |
| Visibility | `Visibility`, `OutboundMessage.visibility`, `RenderedMessage.ephemeral`, `CommandSpec.visibility`, `CommandSpec.opensForm`, the `opensForm` and `visibility` flags of the action registry | C5 |
| Typed command options | `CommandArg.choices`, `CommandArg.autocomplete` | C6 |
| Reactions | `Inbound.ReactionChanged`, `ChatAdapter.react`, `ChatPort.react`, `VendorOp.React`, `VendorOp.UnreactAll`, `ReactPayload`, the `react` outbox operation, `CapabilityProfile.botReactions` and `reactionEvents` | C10 |
| Native select and modal | `ChoiceLayout`, `RenderedControls.SelectMenu`, the values of `Inbound.InteractionSubmitted`, `VendorOp.OpenForm`, `CapabilityProfile.select`, `modal`, `ephemeral` and `deferrable` | C11 |
| Renderer rungs | native select, numbered reactions, modal, the three visibility rungs, the reaction reply-quote finalize rung | C11 |

### Product limits (C3)

`ControlLimits` holds our own bounds, not platform maxima: a choice label has at most 32 characters, a row at most 8 buttons, a message at most 24 buttons. A choice set therefore has at most 24 choices, and the renderer pages a message that would carry more than 24 buttons. A label built from user text is shortened with `ControlLimits.fitLabel`. A form has a title and at least one field, with no cap copied from a platform.

### Frozen surface

| Need | Contract element |
|---|---|
| Send text, a photo or a document | `ChatAdapter.send(chat, rendered, sendKey)`. `RenderedMessage.attachment: Option[AttachmentRef]` carries the photo or document; the first text chunk is the caption; the text may be empty when an attachment is present |
| Idempotency key | `OutboundMessage.dedupeKey` in the core, `sendKey` at the adapter. A multi-part send derives one key per part from it |
| Attachment | `AttachmentRef(kind: MediaKind, assetKey, mimeType, altText, fileName)`. `assetKey` is opaque: the adapter resolves it through the asset store and keys its upload cache by it. `altText` is required and has at most 1024 characters |
| Buttons | `Choice(label, action, style, emoji, hotkeys)` with `ChoiceAction.Callback(token)`, `OpenApp(AppRoute)` or `OpenUrl(url)`, built by `Choice.callback`, `Choice.openApp` and `Choice.openUrl`. The three kinds may share one row. A URL is `https` only |
| Mini App route | `AppRoute(wire)`: 1 to 64 characters of `A-Z a-z 0-9 _ -`. The contract checks the grammar; the screen codes belong to MINI_APP section 3.4 |
| Edit and delete | `ChatAdapter.edit(handle, rendered)` and `ChatAdapter.delete(handle)`, both idempotent by content. An edit never carries an attachment |
| Free text from the user | `Inbound.MessageReceived(text, replyTo, truncated)` |
| Media from the user | `Inbound.MediaReceived(kind: MediaKind, media: MediaRef, caption)`. `MediaRef` is an opaque handle; the bytes stay with the vendor |
| Deep link | `Inbound.ConversationStarted(payload: Option[StartPayload])`. `StartPayload.parse` returns `None` for text outside the grammar (the route grammar above). The payload is attacker-controlled and never grants access |
| Tapped control | `Inbound.InteractionSubmitted(callback, source)` |
| Callback answer | `InteractionHandle.answer(toast: Option[String])`, single shot; `editSource(rendered)`; `acked` tells the mediator whether the answer is spent |
| Capability | `CapabilityProfile.media`: `true` on Telegram, `false` on the console |

Rules that hold on this surface:

1. A link choice (`OpenApp`, `OpenUrl`) never comes back as an inbound event. It is not numbered (`RenderedChoice.index` is 0) and has no `choice_map` row. Callback choices are numbered from 1 across the message.
2. A message with an attachment is always a new message. The mediator drops `replaces` from such a reply, and an adapter may refuse an edit that carries an attachment.
3. Every attachment has a text equivalent. A profile without `media` shows it in place of the image.
4. Every type that crosses `ChatAdapter` round-trips through JSON (CON-01). `InteractionHandle` is the one exception: it is a live handle.

| Shape | Console text |
|---|---|
| Photo attachment | `[image: <alternative text>]` as the first paragraph, then the caption |
| Document attachment | `[document: <alternative text>]` |
| `OpenApp` choice | `[app: <route>] <label>` in the legend, without a number |
| `OpenUrl` choice | `[link: <url>] <label>` in the legend, without a number |

| Block | Ladder |
|---|---|

| Form | `form.formRunner`: one question per message |

## Deviations from ARCHITECTURE section 6

| Row | Section 6 says | Decided here | Reason |
|---|---|---|---|
| C4 | `answer(text, alert)` | `answer(toast)` and the query `acked` | No slice shows an alert yet (BOT_UX BUX-DISC-03 is the first). The mediator needs `acked` to choose between the answer and a message. The alert is added with its consumer |
| C7 | `AttachmentRef` with size, dimensions and hash; `protectContent`, `spoiler` | Kind, asset key, MIME type, alternative text, file name | The asset store owns size, dimensions and hash behind the opaque key. `protectContent` and `spoiler` stay with G4.6 |
| C8 | `Choice` becomes a sum; `AppRoute` is a closed enum; `CopyText` | `Choice` keeps one shape and carries a `ChoiceAction`; `AppRoute` is a checked string; no `CopyText` | Label, style and limits are common to the three kinds. A closed enum in `contracts` would duplicate the route table of MINI_APP. `CopyText` has no consumer |
| C10 | `sendMedia` as an operation | A media-capable `send` | One operation carries one idempotency key, one outbox row and one `choice_map` record for text and for media |
| C12 | `appButton`, `editMedia`, `startPayload` flags | `media` only | Both profiles treat a link choice the same way wherever a choice is shown; no code reads the other flags yet |

## Not decided here

These stay with the slice of their first consumer, each with an addendum to this record: `setMenu` and the menu button (G1.13); `ReachabilityChanged` (G2.15); `protectContent` and `spoiler` (G4.6); an edit that changes or adds an attachment (G6.2, after spike SP-11); `fetchMedia` for the bytes behind a `MediaRef` (G12.6); `CopyText`; the alert form of the callback answer.

Two inherited elements were left in place and are open follow-ups:

1. `Inbound.FormSubmitted`, `Form.submit` and the submit token of the FormRunner. No adapter emits a form submission any more; the FormRunner still builds one internally.
2. The mediator answers a tapped control with no toast before database work (ADR-013), so on a single-shot vendor a handler's toast arrives as a short message. ARCHITECTURE TG-12 moves the early answer into an adapter watchdog; the transport slice decides this with ADR-017.

## Addendum 1 (2026-11-13): toggle keyboard

A multi-select on a profile with buttons is one message whose keyboard is edited in place (row C11, ARCHITECTURE section 7.7). The contract does not change: the renderer puts a multi-select that fits the button budget on the rung `choices.toggleKeyboard`, with no typed-reply instruction, and the producer of the choice set owns the state.

The wizard engine is that producer. On a vendor whose profile has buttons it marks each selected option with a leading "✓ ", appends the choice "Done", keeps the selection in the session, and answers each tap with an edit of the same message. The `step_seq` of the session does not change on a toggle, so a tap made on the keyboard as it was before the edit arrived still counts. "Done" passes the selection to the step in option order; the step validates it as it validates a typed reply. On the console nothing changes: the numbered legend and the typed reply remain.

## Addendum 2 (2026-11-13): typed input on a prompt with choices

The owner typed "9:00" at the add-medication times question on the live bot and could not tell that it failed (BOT_UX section 15.6). The times step that replaced the question offers quick choices and also takes typed times. On such a prompt a bare typed number must stay input: with nine choices on the message, "9" would otherwise resolve to the ninth choice, "Cancel".

The contract gains two fields with defaults, so stored documents of the old shape still decode:

- `ChoiceSet.numberHotkeys: Boolean = true`. False marks a set on a prompt that takes typed input. Its choices are tapped, or typed by label; a typed number is never the number of one of its choices.
- `ChoiceMapEntry.byNumber: Boolean = true`. The renderer copies `numberHotkeys` into each row of `rendered_messages.choice_map`; the mediator resolves a bare or quoted number only against rows with `byNumber`. Label resolution is unchanged.

Console rendering (CON-02): the numbered rung lists such a set as its labels in brackets, `[08:00] [09:00] [Other time]`, with no numbers and no multi-select instruction. On Telegram nothing changes on the wire: the set is an inline keyboard as before.

The wizard engine uses it through `StepKind.Choices(acceptsText = true)`: both the step's set and its Back/Cancel row are rendered with `numberHotkeys = false`, and a typed message goes to the step as text. A `Step` may also name a `rescue` step: after two rejected inputs in a row the engine moves there with the last reason shown, which is how a text-only step hands the user back to buttons of common choices.

Not added: a one-tap location request and an inbound location. PRODUCT_SPEC R-IDC-12 and R-IDC-22, BOT_UX BUX-TZ-03 and research 06 section 7.1 forbid asking for or using the device location; a contract change for it waits for the owner to amend those requirements.

## Alternatives

Keeping the removed concepts behind test-only capability profiles (they were kept that way after the vendor removal; every contract change then paid for rungs that no vendor uses). A separate `sendMedia` operation (a second idempotency path through the outbox and the mediator). A separate block for link buttons (a callback and a Mini App button could not share a row, which BOT_UX section 8.4 needs for rows such as "Stats" and "Open app"). Adding every row of C7 to C12 now (most have no consumer and one depends on a spike).

## Consequences

No reference to a removed concept compiles. The renderer goldens changed and the change is recorded in the commit of the removal; the console transcripts and the 30-day simulation golden did not change. A handler that wants a native control which Telegram does not have uses an inline keyboard or a Mini App screen. Stored `OutboundMessage` and `Reply` documents of the old shape do not decode; no production data exists (ADR-014). The live smoke LS-1 must be repeated on this contract once a Telegram adapter and a bot token exist.
