# ADR-004: Scheduler = materialised dose_occurrences with one next_action_at column, epoch fencing, schedule revisions and a cross-revision live-slot index; no scheduler library

Status: Accepted
Date: 2026-09-11

## Decision

Schedules are append-only schedule_revisions with an exhaustive Rule enum (pause and resume are revisions too); a materialiser expands each active revision 48 h ahead into dose_occurrences rows keyed UNIQUE (schedule_id, revision, local_date, slot_key) and additionally guarded by a partial UNIQUE (schedule_id, local_date, slot_key) WHERE status <> 'cancelled' with revision-stable slot keys, inserting with ON CONFLICT DO NOTHING (no target); edits lock the schedule's open rows FOR UPDATE, default effective_from to the next local midnight when today's slots are touched, and keep rather than cancel old rows that the new revision cannot reproduce. A single loop claims rows with next_action_at <= $now FOR UPDATE SKIP LOCKED, wraps each row in a savepoint (quarantining a failing row instead of stalling the batch), calls the pure exhaustive decide() and writes the state change, the dose_actions row, the outbox rows and the new next_action_at in one transaction with no network calls; send_key includes the epoch and older queued rows for the occurrence are cancelled; heartbeats are one row per instance written after the batch; catch-up collapses to the target state, marks windows without delivery evidence unknown, and folds sends into one digest per account per 15-minute bucket with per-item epochs; a nightly pass re-verifies pending instants against the JDK tzdb.

## Alternatives

Quartz or db-scheduler (job models, not this lifecycle); APScheduler-style job queues; two loops (reminder worker + missed-dose worker) as in the UX doc; rrule-based recurrence libraries; cancelling jobs on edit instead of fencing; a revisioned-only natural key (allows two live doses for one slot across revisions, the blocker found in review); one transaction per batch without savepoints (one poison row stalls every reminder).

## Consequences

Reliability is a property of the data model: idempotent materialisation, exactly-once state transitions, at-least-once sends with UNIQUE send_key, one live dose per slot across edits, pauses and timezone moves, deterministic DST behaviour recorded on the row (dst_kind, local_date, tz), safe multi-worker operation, poison-row isolation and catch-up without floods. The loop is bespoke code (~300 lines) covered by property tests over IANA zones, the restated loop-equivalence contract and a 30-day scenario simulation; the materialised-lag and quarantine alerts are load-bearing from day one.
