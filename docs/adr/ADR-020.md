# ADR-020: Mini App API and frontend contract

Status: Accepted in part (2026-11-13); the chart mechanism is carried, not built
Date: 2026-11-13

## Context

ARCHITECTURE section 9 defines the HTTP API of the Mini App: one origin, the resource list of section 9.5, the conventions of section 9.4 and the hardening of section 9.8. MINI_APP section 15 maps the screens to those resources. ROADMAP slice G3.1 writes this record; G3.3 to G3.7 build on it. This record fixes what the first implementation decided where the documents left a choice.

## Decision

1. **Definitions are the source.** Routes are Tapir definitions in the module `api`. `api/openapi.json` is generated from them and committed. `./mill api.test.runMain dosegram.api.openApiCheck api/openapi.json` fails on a drift, and a test pins every path to the table of ARCHITECTURE section 9.5. The Mini App generates `src/api/schema.d.ts` from the committed document; `pnpm --dir miniapp run api:check` fails on a drift (DEP-09). Both checks run in CI.
2. **One origin.** With `MINIAPP_ENABLED=true` the application opens a second listener (`HTTP_PORT`) for `/app/` and `/api/v1/`; `/healthz` stays on the internal port. The application, not the proxy, sets the header set of research brief 06, section 12.4, on every answer of that origin, so a test covers it. No CORS header is sent.
3. **Errors** are RFC 9457 documents with the closed code list of section 9.4 and a request id. A request that cannot be read (broken JSON, an unknown member, a wrong type, an identifier that is not a UUID) answers 400 `validation_failed` without detail; a readable request with invalid members answers 422 `validation_failed` with `errors: [{field, code}]`. No error echoes input. An unexpected exception answers 500 `internal`; the log line holds the request id and the exception class only.
4. **Authorisation.** Every handler takes the account of the session. A record of another account answers 404, exactly like an unknown one (API-11). A cross-account suite calls every route that takes an identifier, and a registry test fails when such a route has no case.
5. **Idempotency.** A creating `POST` requires `Idempotency-Key` (a UUID). A repeat with the same body returns the stored response; another body returns 422 `idempotency_key_reuse`; only a success is stored; records are deleted after 24 hours (API-16).
6. **Concurrency.** `ETag` is `"v<version>"`. For a medication the version is `updated_at` in microseconds, which the write moves forward by at least one microsecond; for a schedule it is the current revision number. `If-Match` is required on edits: absent is 428, stale is 412 with the current representation in the problem document (API-17).
7. **`PATCH /medications/{id}` carries the whole editable set.** An absent optional member clears the value. The editor always sends the whole form, and a partial update would need a way to tell "absent" from "cleared" that JSON members do not give.
8. **A medication edit reaches reminders.** A reminder is rendered from the dose snapshot of its occurrence. An edit that changes the snapshot appends a schedule revision with the new snapshot, effective at once.
9. **One schedule per medication that has not ended.** The chat menu and the reminder card assume it. A second schedule is refused with `schedule_exists`; ending the schedule frees the medication for a new one.
10. **Charts** (ROADMAP conflict X-30): the server lays out a chart as a scene and the Mini App paints it with DOM calls; no SVG or HTML string is sent for insertion. This is carried from ARCHITECTURE section 9.5.1 and is not built by this record's slices.

## Addendum, 2026-11-13: consent check and durable idempotency records

Two gaps of the list above are closed. The consent check of API-19 exists for the medication domain: every medication, schedule and day route answers 403 `consent_required` with the member `purpose` when the account has no active `medication` consent, and `ConsentApiSuite` fails when a medication route is added without a case. The check and the request run in two transactions; a withdrawal that commits between them is not fenced. Idempotency records are rows of `idempotency_keys` (`PgIdempotencyKeys`, adapted by `PgIdempotencyStore` in `app`): a key is reserved before its request runs, no connection is held while it runs, a second request with the same key waits for the outcome, and a reservation older than 60 seconds is taken over. The stored response is not encrypted until the account keys exist (ROADMAP G2.4b). The policy function, dose actions over HTTP and the routes `POST /consents/{purpose}/requests` and `/withdrawals` are still missing.

## Consequences

- A client and a server cannot drift without one of the two checks failing.
- `updated_at` as a version is a stand-in: any write to the row moves it. When the schema gains a version column the `ETag` format stays and only the source of the number changes.
- The chat pauses a schedule without touching the medication row, so the API derives "paused" from the schedules instead of trusting the column.
