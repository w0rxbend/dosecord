# ADR-013: Interaction acknowledgement policy — ack before work, declared visibility, no defer for form-opening actions, Telegram's answer is single-shot

Status: Accepted
Date: 2026-09-11

## Decision

The mediator acknowledges before the inbound insert and outside the per-chat executor, driven by static declarations: component actions defer with an update; commands defer a reply with the visibility declared on CommandSpec; actions flagged opensForm are not deferred — the mediator verifies the MAC, resolves the principal with one indexed read and opens the modal within the budget, running database work on FormSubmitted; the adapter watchdog acks with the same declared type at 1.5 s (Discord) / 2 s (Telegram) measured from the interaction's creation timestamp and is disabled for opensForm tokens, with an explicit, counted fallback to FormRunner if the deadline is missed. Telegram's profile is transientAck = true, deferrable = false: cheap toasts are computed before any transaction and answered within about 1 s; a later toast degrades to a short auto-deleting message or is folded into the edited reminder. A handler that returns a visibility different from the declared one is delivered as a follow-up message.

## Alternatives

Revision 1's 'defer every interaction immediately' (makes Discord modals unreachable and fixes the wrong ephemeral flag for slash replies); acking inside the keyed executor after the inbound insert (a queued chat eats the 3 s budget); treating Telegram like a deferrable vendor (drops every post-ack toast).

## Consequences

Discord modals work for Add note, Correct time and wizard text steps; /account is ephemeral and /today is not, by declaration; 'This interaction failed' is avoided within the real budget rather than a receipt-relative one; the conformance suite covers modal-on-modal-profile, visibility mismatch, toast-after-auto-answer and deadline auto-ack; ack latency is measured from creation time.

## Addendum (2026-09-23)

M0.8 (Spike C, docs/spikes/jda-dm.md) confirmed this policy's Discord timing assumptions live on JDA 6.6.0 in a bot DM: every acknowledgement landed 102-185 ms from the interaction's snowflake creation timestamp against the 1.5 s watchdog (and the 3 s hard limit), across slash replies, a button edit-as-ack, `replyModal` as the first and only ack on an un-acked interaction, and the modal submit's reply. No change to the policy; the USER_INSTALL-only registration decision is recorded in the ADR-001 addendum of the same date.

## Accepted addendum — UX-00 (issue #2)

An acknowledgement is not a persisted outcome. M2.2 includes the minimum
vendor-neutral interaction contract and mediator repairs needed for its
retained end-to-end acceptance: deferred reply completion, declared visibility,
modal-deadline recovery and independently acknowledged restart-safe submits.
M2.2a adds durable source-edit/uncertain-outcome recovery and failure/retry
hardening after that working vertical; required M2.2 repairs cannot be
allocated only to its dependent slice.
No defer before opening a modal; missed deadlines persist FormRunner state
and count degradation. Rendering/upload/DB work remains off the listener and
ack critical path under Ox. Routine navigation, setup, history, outcomes and
requested reports are silent; reminders obey persisted notification policy.
Do not emit a second toast plus persistent success or promise success before
readback-confirmed commit. Expired hooks cannot preserve ephemeral promises;
private named details must not silently become persistent disclosure.

## M2.2a recovery protocol (issue #12)

Source replacements enqueue `edit` with the encoded source handle, not `send`.
Interaction-reply payloads retain the originating ChatRef as a backward-compatible
`deliveryChat` field; new/unlinked replies never guess a primary channel after
restart. Private native-hook payloads still have no ordinary safety row.
A typed nonfatal `PermanentReason.MissingTarget` alone permits one persistent
replacement for a persistent source edit; generic permissions/fatal errors do
not. The replacement uses a stable `:replacement` send subkey. Its handle and
callback map are recorded before terminal dispatcher bookkeeping; lease retry
and stored-reply replay use the recorded handle. Vendor nonce dedupe is bounded,
not permanent exactly-once delivery: a create accepted before its handle write
can still duplicate outside the provider dedupe window (ADR-009).

On an SQL exception, show neutral `Checking whether this was recorded…` and
attempt one durable inbound/recorded-handle readback. A confirmed stored reply
is replayed without rerunning the handler or appending/publishing domain events.
Absent/unavailable readback remains unconfirmed; it is not evidence for
`Nothing was recorded` and does not trigger a blind handler retry. A later
same-vendor-event replay passes through the durable inbound uniqueness guard.
A reply bookkeeping failure after a confirmed commit is delivery recovery, never
a failed domain action. Dispatcher retries retain the existing eight-attempt
budget. M2.2b executable ownership, M2.2c complete page bookkeeping and wider
navigation/draft/manual-intent work remain outside this protocol.
