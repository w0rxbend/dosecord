# ADR-019: Own thin Telegram client and the adapter built on it

Status: Accepted
Date: 2026-11-13

## Context

The product talks to one vendor, the Telegram Bot API (ADR-014). The repository rule is that `core` and `contracts` stay free of vendor symbols and that no log line carries a credential, a message body, a medication name or a note. The Bot API puts the bot token into every request URL (research brief 02, section 3), its error codes are "subject to change", and most error descriptions are not in the reference (ARCHITECTURE section 7.10). No bot token exists yet, so everything had to be built and proven without the live API.

Research brief 02, section 22, compared the JVM client libraries. Each of them brings its own HTTP stack and JSON library, logs or exposes request URLs in some path, and models far more of the API than the product uses.

## Decision

`adapter-telegram` contains a hand-written client and has no dependency of its own: the JDK HTTP client and the uPickle that `contracts` already brings.

| Element | Decision |
|---|---|
| Transport seam | `TelegramTransport.call(WireRequest): WireReply`. `HttpTelegramTransport` is the only file that imports `java.net.http`. A failed call is a `WireFailure` without the HTTP client's message, because that message can quote the URL |
| Token | `BotToken` is readable inside the adapter package only and prints as `BotToken(***)`. Its form is checked at construction, so building a request URL cannot fail with a message that quotes it |
| Codecs | Hand-written `ujson` decoders for the types in use. An unknown field is ignored; an unknown update kind and a known kind with a malformed body decode to `UpdateBody.Unknown` (TG-01) |
| Errors | `TelegramError` is a closed enum. No case carries the description text, because a description can quote the request. `TelegramErrorMapper` maps a status and a description to exactly one case, and one case to at most one `ChatError` |
| Fake wire | `FakeTelegramTransport` in the main sources: it records calls, answers the methods in use, serves queued updates, plays scripted replies and can enforce a per-chat flood limit. The launch-path tests of `app` run the assembled application on it |
| Fixtures | `adapter-telegram/test/resources/telegram/fixtures`. They have the documented shape and were written by hand; they are replaced by recordings when the live spike of ROADMAP G1.1 runs |

Decisions of the adapter that the contract leaves to it:

1. A message handle says what kind of message it names: `<id>` for a text message, `m<id>` for a photo or a document. The adapter keeps no state, and a media message is edited through `editMessageCaption`.
2. The single callback answer. The mediator answers a tap with no toast before database work (ADR-013), and a handler's toast comes later; Telegram shows one answer. The adapter therefore holds a neutral answer back for a grace time (300 ms, configuration). A toast that arrives inside it is the answer that goes on the wire; otherwise the neutral answer goes out. A watchdog started at receipt sends the neutral answer at 1.5 seconds whatever happened (TG-12), and a query older than 30 seconds is not answered at all (TG-11). `InteractionHandle.acked` reports whether the answer is spent on the wire. ADR-017 may replace the grace time by an answer the mediator sends after the handler.
3. A 429 pauses the chat inside the adapter for `retry_after`: until then a message call for that chat fails with `RateLimited` and nothing goes on the wire (TG-28). Message calls pass a per-chat and a global token bucket, callback answers a separate one (TG-25, TG-26).
4. `sendKey` is not sent to Telegram, which has no idempotency key for a send. The outbox protocol of ADR-009 bounds duplicates (TG-19).
5. An attachment whose bytes the asset store does not have is sent as its text equivalent, `[image: <alternative text>]` and the caption. The asset store is a port of the adapter (`MediaStore`); the `file_id` cache is in memory until the schema has `telegram_file_cache`.
6. The webhook is a function of the request (`WebhookHandler`): constant-time comparison of the path secret and the header secret, the body limit, and 200 only when the update is stored. It is not mounted, because the durable inbox of ROADMAP G1.7 does not exist yet; long polling is the only ingestion path the executable serves.

## Alternatives

`pengrad/java-telegram-bot-api`, `rubenlagus/TelegramBots` and the Scala wrappers (research brief 02, section 22): a second HTTP and JSON stack, token-bearing URLs outside our control, and a release cadence that decides when a new Bot API field breaks decoding. Generating a client from the published schema: forty methods in use do not pay for a generator. Answering the callback at once and sending every later toast as a message: each stale tap would leave a message in the chat.

## Consequences

A new Bot API method costs a request builder and a decoder. Error strings are assumptions until a live spike records the real ones; the mapper is one table and its fixtures are one file. The grace time adds up to 300 ms before the progress indicator of a tap without a toast stops. A restart loses the timers that remove short-lived messages and the `file_id` cache.
