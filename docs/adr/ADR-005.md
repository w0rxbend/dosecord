# ADR-005: Vendor adapters are decoupled from the core by a ChatMediator with a capability-driven renderer in the core

Status: Accepted
Date: 2026-09-11

## Decision

The core exposes one inbound event enum, one abstract OutboundMessage (RichText AST + ChoiceSet/Form/Notice blocks) and one ChatPort; adapters implement a small blocking ChatAdapter trait, declare a static CapabilityProfile (including transientAck, deferrable, delete/edit windows and an events-per-message budget), and throw a closed ChatError hierarchy with a channelFatal flag. A pure Renderer in the core lowers messages through fixed degradation ladders (buttons -> select -> numbered list with at most 3 bot-added reactions -> numbered list; modal -> sequential FormRunner; ephemeral -> deleteAfter -> notice; edit -> remove own reactions + reply-quote on the reaction tier -> replacement with superseded_by). Reactions and quoted-reply numbers resolve in the mediator via rendered_messages.choice_map by target handle unconditionally; bare digits use the latest-prompt gate. Vendor identity is an open string; adapters are Mill modules that depend only on contracts and core; a console adapter ships first as the boundary proof.

## Alternatives

Per-vendor rendering inside adapters; a lowest-common-denominator text-only contract as today; a closed Platform enum in contracts; adapters calling domain services directly; the latest-prompt gate applied to reactions (kills reactions on old reminders, the review finding).

## Consequences

Adding Telegram, Zulip or Matrix is a new module plus one settings entry, verified by the shared adapter conformance suite and by the rule that the Telegram slice must touch zero core files; the renderer golden files per profile become the cross-vendor UX spec; Zulip and Matrix get a real one-tap loop via pre-added reactions within Synapse's burst limits; the mediator is a stateful component with six tables, so v1 assumes the modular-monolith deployment sharing one database.
