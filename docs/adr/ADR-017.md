# ADR-017: Telegram ingestion and acknowledgement

Status: Accepted
Date: 2026-11-13

## Context

Until this record, a polled Telegram update went from `getUpdates` straight into the mediator's in-memory per-chat queue, and the reader moved its offset as soon as the queue took the update. A process that died after the offset moved and before the mediator's transaction committed lost the update: Telegram would not send it again, and nothing in the database held it. The webhook handler was a pure function that nothing mounted (ROADMAP G1.6 status note). ARCHITECTURE section 7.2 describes the target: one durable inbox for both delivery paths, 200 only after commit, per-chat ordered processing, and ADR-013's "acknowledge before database work" kept. ROADMAP G1.7 builds the skeleton of it with one webhook connection and no reorder window.

## Decision

1. **One inbox for both paths.** Every update that a long poll or the webhook receives is stored in `inbound_inbox` (migration `V3__inbound_inbox.sql`), keyed `(vendor, vendor_event_id)` with `vendor_event_id = telegram:update:<update_id>`, the key the mediator's `inbound_events` uses, by an `INSERT ... ON CONFLICT DO NOTHING` that commits on its own. The poll offset moves past an update, and the webhook answers 200, only after that insert returned. A failed insert keeps the offset (the next poll brings the update again) or answers 503 (Telegram retries). A duplicate delivery finds the row and changes nothing (TG-04).
2. **What is stored is what is read.** The body is the decoded update written back as the minimal JSON the adapter's decoder reads (`InboxCodec`), not the body Telegram sent: names, usernames and the language code are never stored. Decoding the stored body gives the same update. The body still holds message text and callback data until it is processed; its encryption at rest is G2.4b.
3. **Screening at receipt.** A sender outside the allowlist of G1.6 gets the fixed reply at receipt and nothing is stored. An update that can never become an event (a group message, an unknown kind) is logged by its kind and dropped; a callback without usable data is answered. Only an update that becomes an event is stored.
4. **The processor.** `InboxProcessor` (`core/chat`, vendor-neutral) takes, per chat, the pending entries in `update_id` order and hands each to the adapter, which maps it and calls the mediator's new `pushAndWait`. That call takes the event's place in the mediator's per-chat queue, as `push` does, and returns when the event's transaction has committed (true) or failed (false). The inbox row is marked processed, and its body deleted, only after a true. Chats run concurrently, the entries of one chat one at a time; a failed entry holds back its chat; the third failure quarantines it and counts `dosegram_inbox_quarantined_total` (TG-06, TG-09). The processor wakes when an update is stored and polls once a second otherwise. It runs in the gateway half.
5. **Exactly once, and the reply at least once.** A process that dies between the store and the processing leaves the row pending; the next process processes it. A process that dies between the mediator's commit and the mark leaves the row pending too; the next process offers it again, the mediator finds its `inbound_events` row and replays the stored reply without running the handler (TG-08). The effect is therefore applied once; the reply message can be sent twice in that window, because whether the first one reached Telegram is unknown.
6. **Acknowledgement.** ADR-013's "acknowledge before database work" is kept: the mediator answers a callback before its transaction, now after the inbox insert and the processor's pickup. The age limit of TG-11 is measured from the inbox's receipt time, so a callback processed after a restart is not answered late.
7. **Webhook.** `POST /tg/webhook/{path_secret}` is mounted on the HTTP edge (the Mini App listener when `MINIAPP_ENABLED`, a listener of its own otherwise) when `TELEGRAM_UPDATES_MODE=webhook`. The path secret and the `X-Telegram-Bot-Api-Secret-Token` header are the endpoint's security input and are compared in constant time before the body is read; a wrong or missing one is 404. The body is limited to 1 MiB (413). Start-up calls `setWebhook` with the URL under `PUBLIC_BASE_URL`, the header secret, the four `allowed_updates` and `max_connections` 1, and never `deleteWebhook`; in poll mode only a development bot's webhook is deleted (G1.6). Long polling stays the default of development.
8. **Deletion.** The worker half deletes every inbox body 24 hours after receipt, quarantined and pending ones included (a pending one becomes `expired`), and every inbox and `inbound_events` row after 7 days (ARCHITECTURE section 15.6).

## Rejected alternatives

- Processing inside the webhook request: Telegram's response deadline is undocumented, and a slow handler would make Telegram retry an update that was applied.
- Storing Telegram's body as received: it holds names the product does not collect.
- Marking the inbox row from the mediator's transaction: it would put a store of the edge into the transaction of a chat event, against ARCHITECTURE section 10.17; the mediator's own key already makes a second delivery harmless.

## Consequences

- Not built here: the reorder window of TG-07 and `max_connections` above 1 (G2.18), drift detection of the webhook (G2.18), rotation of the header secret with two valid values (the handler accepts a list; the settings carry one), the `NOTIFY` wake across processes, encryption of the body (G2.4b), and a lease for more than one gateway process on the same database.
- The live smoke of the webhook (LS-2) needs the staging origin of G1.8.
