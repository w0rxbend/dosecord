# ADR-002: PostgreSQL 18 via pgjdbc + HikariCP with hand-written SQL and Flyway migrations

Status: Accepted
Date: 2026-09-11

## Decision

PostgreSQL 18 (postgres:18-alpine; supported to 2030-11) is the only stateful dependency. Access through pgjdbc 42.7.13 and HikariCP 7.1.0 with SQL written by hand through a ~150-line in-repo interpolator and row mappers (no ORM); schema managed by Flyway 13.6 plain-SQL migrations run at startup under pg_advisory_lock, with `flyway validate` in CI. All instants are timestamptz written from the injected Clock; status columns are Postgres enums or CHECK constraints; audit tables are INSERT-only for the app role. A dedicated connection runs LISTEN for the wake-up channel.

## Alternatives

PostgreSQL 17 (a year less support on a greenfield deployment for no reason); SQLite (no SKIP LOCKED, LISTEN/NOTIFY, partial indexes or safe multi-process writers); Magnum (2.0.0-M3 milestone) or Doobie/Skunk (cats-effect, contradicts direct style); ScalaSql 0.3.2 (viable for read models later; the scheduler's dozen hot statements are clearer as explicit SQL); create_all as today (no migrations).

## Consequences

The scheduler, outbox, idempotency and audit all rely on Postgres semantics (row locks, savepoints, partial unique indexes, jsonb, enums, triggers); one backup story (nightly pg_dump -Fc plus optional restic) that also covers the Matrix repository when it lives in Postgres; the 13 existing models become Flyway V1 after correcting naive timestamps and adding uniqueness and CHECK constraints; expand/contract migrations are required for upgrades.
