# ADR-002: PostgreSQL 18 via pgjdbc + HikariCP with hand-written SQL and Flyway migrations

Status: Accepted
Date: 2026-09-11

## Decision

PostgreSQL 18 (postgres:18-alpine; supported to 2030-11) is the only stateful dependency. Access through pgjdbc 42.7.13 and HikariCP 7.1.0 with SQL written by hand through a ~150-line in-repo interpolator and row mappers (no ORM); schema managed by Flyway 13.6 plain-SQL migrations run at startup under pg_advisory_lock, with `flyway validate` in CI. All instants are timestamptz written from the injected Clock; status columns are Postgres enums or CHECK constraints; audit tables are INSERT-only for the app role. A dedicated connection runs LISTEN for the wake-up channel.

## Alternatives

PostgreSQL 17 (a year less support on a greenfield deployment for no reason); SQLite (no SKIP LOCKED, LISTEN/NOTIFY, partial indexes or safe multi-process writers); Magnum (2.0.0-M3 milestone) or Doobie/Skunk (cats-effect, contradicts direct style); ScalaSql 0.3.2 (viable for read models later; the scheduler's dozen hot statements are clearer as explicit SQL); create_all as today (no migrations).

## Consequences

The scheduler, outbox, idempotency and audit all rely on Postgres semantics (row locks, savepoints, partial unique indexes, jsonb, enums, triggers); one backup story (nightly pg_dump -Fc plus optional restic) that also covers the Matrix repository when it lives in Postgres; the 13 existing models become Flyway V1 after correcting naive timestamps and adding uniqueness and CHECK constraints; expand/contract migrations are required for upgrades.

## Addendum (2026-11-13) — the schema baseline is frozen

Context: the owner began live use on 2026-11-13. A database created from the baseline now holds real data, so an in-place edit of `V1__baseline.sql` changes the checksum Flyway recorded and the next start refuses it. ROADMAP questions RQ-2 ("no database must be preserved; the baseline is edited in place until CP2-f") and RQ-13 ("freeze at CP2-f with tag `0.1.0-rc.1`") are superseded by that live use: the baseline froze on 2026-11-13, before CP2-f and before the reshape slices G2.2 to G2.4b.

Decision:

- `V1__baseline.sql` is frozen at the schema the owner's live database was created with: the file of commit `d57873f`, Flyway checksum `1193628809`. The local Git tag `schema-baseline-v1` marks the commit that recorded the freeze. The tables `day_profiles`, `prompt_schedules` and `prompt_occurrences`, which a later merge had written into the baseline in place, moved unchanged into `V2__day_profile_nudge_plans_and_prompts.sql`.
- Every schema change from now on is a new versioned migration, `V2`, `V3` and so on, in expand-and-contract form. A committed migration is never edited, and `flyway repair` is never used.
- `scripts/check-frozen-migrations.sh` compares every migration with the SHA-256 recorded in `scripts/frozen-migrations.sha256` and fails on a changed, missing or unlisted file. It is part of the standard gate (ROADMAP section 0.6) and a CI job. A new migration is listed in the commit that adds it.

Consequences: a slice that the roadmap describes as an in-place edit of the baseline (G1.7, G2.2, G2.3, G2.4, G2.4b, G2.8, G2.16 and the others) writes a new migration instead, and a rename or a removal of a column needs the expand-and-contract steps. A database created from a pre-freeze baseline (any commit before `d57873f`) is not upgradable by Flyway and is moved by copying its rows, as the owner's first live database was. ARCHITECTURE section 10.17 holds the rules for a track that adds tables.
