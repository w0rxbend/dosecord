# ADR-011: Time is per-schedule IANA zone with explicit gap/fold policies via java.time, injected clocks, and the JDK tzdb tracked as a metric

Status: Accepted
Date: 2026-09-11

## Decision

Each schedule revision stores its own IANA zone (tz_follows_user decides whether a user zone change re-revisions it); wall times resolve with ZoneRules.getTransition: no transition -> plain; gap -> ZonedDateTime.ofLocal shifts forward by the gap length (same result as Python's zoneinfo fold=0 and Temporal 'compatible'); overlap -> the earlier offset; dst_kind in (none, gap, fold) plus local_date, local_time and tz are stored on every occurrence; interval_fixed_start resolves its anchor per local day, chain arithmetic is pure instant arithmetic; all instants are timestamptz in UTC; every service and query takes now from an injected Clock; the JDK tzdb version is a metric and a nightly pass re-verifies pending instants.

## Alternatives

Account-wide timezone only; SQL now() as the time source; a round-trip check alone (detects gaps but not folds, so revision 1 could not explain a fold choice); continuous instant arithmetic for fixed-start intervals (shifts every dose by an hour after each transition); hand-written golden rows (revision 1's Kyiv 02:30 example was wrong — the gap is 03:xx).

## Consequences

Cross-language agreement on DST defaults; golden rows are generated from ZoneRules transitions for Europe/Kyiv, Europe/London, America/New_York, Australia/Lord_Howe, Asia/Kolkata, Pacific/Apia and America/Sao_Paulo so they cannot be hand-written wrongly; a government rule change is handled by the short horizon plus the nightly pass; tzdata updates arrive with JDK patch releases, which must be tracked.
